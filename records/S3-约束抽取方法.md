# S3 · 约束抽取方法与数据规格

> 目标：从 vLLM 源码自动抽取"参数约束图"，每条约束带源码证据，可直接转换为调优器采样约束。
> 硬约束（项目索引）：**无证据的约束一律丢弃**；每条约束后续必须过 S4 沙箱验证。
> 当前引擎锚点：**vLLM v0.30.0**（commit `ced6857afa0ea7b2e3f0846a62e1394e90f15607`），源码 `代码/third_party/vllm-v0.30.0/`

---

## 一、流水线（4 段）

```
① 参数清单（静态 AST）    scripts/extract_params.py        → 实验记录/参数清单.json
        ↓  （config 类字段 + EngineArgs 字段 + CLI flags，全部带 file:line）
② 约束候选（静态扫描）    scripts/scan_constraint_candidates.py → 实验记录/约束候选_静态.json
        ↓  （assert / if-raise；分层：config > engine/core > 其他）
③ 结构化抽取（Agent）     每模块一个 sub-agent 读源码 → 实验记录/S3_parts/<module>.json
        ↓  （把代码级校验翻译成参数级约束，含证据与语义解释）
④ 合并与一致性校验        scripts/merge_constraints.py    → 实验记录/约束图.json
        ↓  （证据行号存在性、参数名存在性、表达式可解析性）
（S4 沙箱证伪）            run_one / 引擎校验路径          → 实验记录/已验证约束.json
```

## 二、约束图数据规格（`约束图.json`）

```jsonc
{
  "meta": {"engine": "vllm", "version": "v0.30.0", "commit": "ced6857...", "generated_at": "..."},
  "nodes": [
    {
      "id": "C001",
      "type": "inequality",            // inequality | implication | mutual_exclusion | range | enum | type | arithmetic
      "expr": "max_num_batched_tokens >= max_num_seqs",
      "params": ["max_num_batched_tokens", "max_num_seqs"],
      "scope": "scheduler",            // scheduler | cache | parallel | model | engine | ...
      "severity": "error",             // error | warning
      "mechanism": "batch 组装时每条序列至少 1 个 token",   // 为什么成立（人话）
      "evidence": [
        {"file": "vllm/config/scheduler.py", "line": 123, "snippet": "if self.max_num_batched_tokens < ..."}
      ],
      "extraction": {"source": "static-candidate+agent", "candidate_kind": "if-raise", "confidence": 0.9},
      "validation": {"status": "unverified", "method": null, "run_id": null, "note": null}
    }
  ],
  "stats": {"total": 0, "by_type": {}, "by_scope": {}, "with_evidence": 0}
}
```

**字段规矩**
- `expr` 一律用**参数真实字段名**（snake_case，如 `max_num_batched_tokens`），不用 CLI 连字符形式；CLI 映射统一查 `参数清单.json`。
- `evidence` 至少 1 条；`snippet` 必须能在该行原文中找到（合并脚本校验）。
- `validation.status`：`unverified` → `confirmed`（违反它真报错）/ `refuted`（不报错）/ `out_of_scope`（仿真器无关，留作真实引擎证据）。
- 每条约束必须能回答：**违反它会怎样**（报错？OOM？静默退化？）——若说不清，标注 `severity=warning` 或剔除。

## 三、Agent 抽取的角色分工（本 session 用 opencode sub-agents 模拟 deepagents）

| 角色 | 输入 | 输出 |
|---|---|---|
| 模块检索 Agent（每模块一个） | 该模块的静态候选列表 + 源码路径 | 该模块的结构化约束 JSON（含证据与机制解释） |
| 判定 Agent（我，主控） | 各模块 JSON | 合并、去重、冲突处理、置信度校准 |
| 审计（G1） | 合并后的随机 20 条 | 逐条打开源码核对 → `实验记录/G1-约束抽检-第一批.md` |

> 说明：本轮先用"静态候选 + sub-agent 精读"的混合方案（对应 G1 不过时的预案 B）；若效果达标，下一轮可直接升级为 deepagents 全自动管线（同一 schema）。
